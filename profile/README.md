# 開発規範

プロジェクトをまたいで全員が守ること。ツール固有の規約（UE / TouchDesigner / スクリプト）は別ページ。
納得できないルールがあれば提案する。黙って無視しない。

## 要約

- 「前例がそうだった」を理由にしない。踏襲するなら、なぜそうなっているか説明できること
- わからないことは「わからない」と言う
- 名前は中身を知らない人が読んで分かるものにする。`新しいフォルダー (2)`、`test2`、`final_v3` は禁止
- 退避フォルダ・バックアップコピーを作らない。不要なら消す。履歴は SVN にある
- 修正は原因を取り除く。症状を隠す修正はしない
- コミットは意味のある単位。「何を・なぜ」を書く。壊れた状態をコミットしない
- 決めたこと・失敗したこと・具体値は Notion に残す
- 「できました」には確認内容を添える
- 戻せない操作は実行前に確認する
- 認証情報をコード・ログ・チャット・Notion に書かない

---

## 1. 考えることをやめない

**前例を理由にしない。** 「他の人がそうやっていた」「前のプロジェクトではそうなっていた」は、判断しなかったことの言い訳にならない。前例は当時の制約下での答えであって正解ではない。納期も人数もツールのバージョンも今回とは違う。理由を知らずにコピーすると欠点ごと引き継ぎ、壊れたときに誰も直せない。

踏襲するのは構わない。ただし「なぜそうなっているか」を説明できる状態で踏襲する。

- NG：「前回の構成をそのままコピーしました。中身は見ていません」
- OK：「前回の構成をベースにした。`Legacy/` は今回使わないので外し、収録データ用に `Recordings/` を足した」

**わからないことは「わからない」と言う。** 推測を断定口調で言わない。「わかりません、確認します」か「〇〇だと思うが未確認」。推測が事実として伝わると、その上に次の判断が積み上がり、本番で発覚したときの手戻りが大きくなる。

**結論から言う。** 報告・質問・相談は、何が起きたか／何を決めてほしいかを先に言い、経緯は後。

- NG：「昨日の夜に試していて、まず A をやって、それから B をやったら……で、動きませんでした」
- OK：「〇〇が動かない。原因は △△ と思うが未確認。確認に 1 時間ほしい。経緯：A → B を試した」

## 2. 命名

名前は最も読まれるドキュメント。作った本人以外が見て、中身と役割が分かること。本人も 3 ヶ月後には忘れる。
数字や記号を足しただけの名前、デフォルト名のままは禁止。

| NG | 何が困るか | OK |
|---|---|---|
| `新しいフォルダー (2)` `Untitled` `NewBlueprint` | 情報がゼロ | `StageLighting_Act2` `BP_StageLightController` |
| `test2` `aaa` `tmp_final_v3_fix` | どれが本物か分からない | `CameraSwitcher_OscBridge`。捨てる物なら期限内に捨てる |
| `data1.csv` `output.mp4` | 何のデータか不明。同名で上書き事故が起きる | `setlist_20261019_rehearsal.csv` `act2_cam3_takeB.mp4` |
| `a` `temp` `flag2` | 型も用途も分からない | `isLiveLinkConnected` `retryCount` `targetFps` |

基本：

- 具体的な語を選ぶ。`get` より `fetch` / `download` / `compute`。`data` より `recordedFrames`
- 真偽値は質問形。`isVisible` `hasAudio` `canRetry`
- 単位を入れる。`delayMs` `heightCm` `timeoutSec`
- 否定形を避ける。`isNotReady` ではなく `isReady`
- 省略しない。`cfg` → `config`、`mgr` → `manager`。定着した略語（OSC, NDI, FPS, BP）は可
- 日付は `YYYYMMDD`。ソートが時系列になり、月日が曖昧にならない
- `_v2` `_final` `_old` `_backup` を名前に付けない。履歴は SVN。例外は外部に渡す成果物の版（`Deliverable_20261019_r2`）

ここに書いたことは『リーダブルコード』（Boswell / Foucher, O'Reilly）の 2〜4 章に全部書いてある。未読なら読む。コードを書かない人も 1〜4 章は命名の話なので読む。

ツールごとの接頭辞（`BP_` `M_` `T_` `NS_` 等）や大文字小文字は各ツールの規約ページに従う。

- Unreal Engine：Allar の UE5 Style Guide がベース
- TouchDesigner：規約ページ未作成
- スクリプト類：規約ページ未作成

## 3. フォルダ構成

ファイルは「そこにある理由」が言える場所に置く。とりあえずルート、デスクトップに置いたまま、は禁止。置き場所も名前と同じく情報で、構造が崩れると「これは消していいのか」を誰も判断できなくなる。

**退避フォルダを作らない。** `_old/` `backup/` `使わない/` は、誰も中身を把握していないゴミ箱になる。不要になったら消す。消すのが怖ければ先に SVN にコミットしてから消す。

- NG：`Content/Old/` `Content/Old2/` `Content/使ってない/` が併存
- NG：`main.py` `main_backup.py` `main - コピー.py`
- OK：残す物だけがある。試行錯誤はローカルでやり、必要になったら履歴から取り出す

新規プロジェクトの構成は、前例をコピーして終わりにしない。今回要るもの／要らないものを見直してから作る。変えた箇所は README かプロジェクトの Notion に 1 行残す。

## 4. 修正の規律

修正に入る前に自問する。2〜5 のどれか 1 つでも NG なら付け焼き刃。原因に戻る。

1. 原因を 1 文で言えるか。「〜が〜の状態で〜を呼ぶから壊れる」
2. この修正は原因を取り除くか、症状を隠すだけか
3. 3 ヶ月後の自分が「なぜこの書き方？」と思う行を含むか
4. 同じ種類のバグが他にもあるとして、同じ修正で直るか
5. 過去に似た問題がなかったか。記録を見たか

症状を隠す修正は「直った」ように見えて原因が残る。別の条件で再発し、隠した分だけ見つけにくくなる。

禁止：

- 根拠のないマジックナンバー。「0.3 秒待てば動いた」の 0.3 を理由なしに埋め込む
- エラーの握りつぶし。`try / except: pass`、エラー出力を消すだけ
- `TODO` と書いて放置
- 「後で変数化する」と言ってハードコード
- 新旧の分岐を「一応残しておく」
- 「多分これで直る」で先に試す。3 回ダメなのに同じアプローチを続ける
- 90% 同じ関数・ノードを新規に作る

**hotfix。** 本番直前など根本対応の時間がないときは認める。条件は 3 つ。関係者に「hotfix、根本は別途」と言う。コード／ノードに `HOTFIX:` と追跡先を書く。本番後の最初の作業で根本対応する。hotfix が悪いのではなく、hotfix だったことを誰も知らない状態が悪い。

## 5. SVN

**1 コミット = 1 つの意味のある変更。** メッセージは「何を・なぜ」。「修正」「更新」「WIP」だけは禁止。問題が起きたときにどのコミットが原因か特定できない。

- NG：`修正` `update` `aaa` `とりあえず`、1 日分をまとめて 1 コミット
- OK：`カメラ切替の OSC 受信をメインスレッドで処理するよう変更（別スレッドからの Actor 操作でクラッシュしていたため）`

**壊れた状態をコミットしない。** ビルドが通らない、プロジェクトが開けない状態を入れると、他人が更新した瞬間に作業が止まる。コミット前に「開く・動く」を確認する。

**入れないもの。**

- 生成物・キャッシュ：`Saved/` `Intermediate/` `DerivedDataCache/` `__pycache__/`。ignore で除外
- 認証情報・鍵・`.env`
- 個人環境専用の設定（絶対パスが埋まったもの）
- 試行錯誤の途中ファイル

**バイナリはロックを取る。** `.uasset` `.toe` `.psd` などマージできないファイルは、編集前にロックするか、編集することを先に言う。衝突したらどちらかの作業が消える。ロックの手順・対象は SVN 運用ページに書く（未作成）。

## 6. 記録

**決めたことは残す。** 仕様・構成・運用で決めたことは、口頭やチャットで終わらせずプロジェクトの Notion に書く。何を・なぜ・いつ・誰と、で 1〜3 行。チャットは流れる。本番 2 週間前に「あれどうなったんでしたっけ」が起きると決め直しになり、前と違う結論になることがある。

**失敗も残す。** 試してダメだった方法は「何を試して、なぜダメだったか」を書く。書かないと別の人が同じ失敗をもう一度やる。

**具体値を残す。** IP・ポート・パス・設定値・バージョン。「設定済み」は本人以外に意味がない。本番当日に本人が不在でも復旧できる状態が目標。

書く場所：

- プロジェクト固有のこと → そのプロジェクトの Notion
- プロジェクト横断の知見・手順 → チームの技術 Wiki（場所は要確認）
- 本番のトラブルと対処 → 本番後のふりかえり

---

## 7. 完了と確認

**「できました」には確認内容を添える。** 書いたと動くは別。自己申告だけの完了は完了ではない。確認内容があれば、受け取る側は何が未確認かを判断できる。

- NG：「カメラ切替、実装しました」
- OK：「カメラ切替、実装した。確認：OSC で 1〜4 を送って切り替わる、連打しても落ちない（30 回）。未確認：Live Link 切断中の挙動」

**戻せない操作は実行前に確認する。** 削除・上書き・本番データの変更・設定の初期化。迷ったら聞く。戻せる操作の失敗は時間の損失で済むが、戻せない操作の失敗は本番の素材を失う。

**既存のものを変える前に現状を見る。** 「たぶんこうなっているはず」で変更しない。

---

## 8. 安全

**認証情報を書かない。** パスワード・トークン・API キー・鍵を、コード・ノード・ログ・チャット・Notion・コミットに書かない。一度出たものは消しても履歴に残り、全部無効化して再発行するまでシステムが止まる。置き場所はパスワード管理ツール（要確認）。

**本番データを変える前にバックアップを確認する。** 取れていなければ先に取る。

**`rm -rf` の類を使わない。** パス 1 文字の打ち間違いでフォルダが丸ごと消える。ゴミ箱経由か、対象を 1 つずつ指定する。

---

## 9. コミュニケーション

**質問には調べたことを添える。** 「動きません、どうすればいいですか」だけは禁止。何を調べて、どこまで分かって、何が分からないか。答える側が同じ調査をやり直すことになる。書いている途中で自己解決することも多い。

**聞かれたことに答える。** 関連する別の話は、答えた後。

**間違いは早く・直接言う。** 自分のミスも他人のミスも、気づいたらすぐ言う。責めるためではなく直すため。本番で見つかったときが一番高い。
